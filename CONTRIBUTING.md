# Contributing to HousemanFS

Thanks for considering it. This project has an unusually strong opinion about a few things, so
please read the hard rules before opening a pull request.

## Getting set up

1. Install Rust via [rustup](https://rustup.rs).
2. `cargo build && cargo test`

The toolchain is pinned in `rust-toolchain.toml`, so rustup will select the right version
automatically.

## Hard rules

These are not style preferences. A pull request that breaks one will be declined regardless of
how good the rest of it is.

### 1. Nothing writes to a scanned volume

The first release is read-only, and that is enforced by an automated test asserting zero
create, write, delete and set-info operations against scanned volumes — not by code review.
If you are adding something that needs to write, it is out of scope for now; open an issue to
discuss it instead.

### 2. Never commit real filesystem data

This is the rule most likely to be broken by accident, so read it twice.

An index is a map of somebody's machine. So is a golden test image, and so is an evaluation
set. Committing any of them publishes file names, paths, sizes and timestamps.

- Test fixtures must be **synthetic** — generated by a committed, deterministic script from a
  fixed seed — or **anonymized** before they enter the repository.
- Evaluation sets must not contain real paths. If a real capture is genuinely required, it goes
  through an anonymizer that is itself tested, and it needs human review before merging.
- Scan artifacts are gitignored. Keep it that way.

### 3. Every claim carries provenance

If the code reports a number to a user, it must be able to say which measurement produced it.
A figure with no traceable source is a bug, not a shortcut.

### 4. Reclaim estimates come from measurement

Bytes-freed figures must be derived from a measured free-space delta, never from arithmetic on
file sizes. The two differ sharply whenever storage is shared, and reporting the optimistic one
is precisely the failure this project exists to fix.

## Commit conventions

Keep the history readable. One commit per logical change.

- Imperative subject line, under ~72 characters: `add extent-aware size accounting`
- Body explains **why**, not what — the diff already says what.
- Conventional prefixes where they help: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`,
  `chore:`
- No work-in-progress commits on `main`. Keep scratch work uncommitted until it is coherent.
- No force-pushes to shared branches.

## Pull requests

- Keep them focused. One concern per pull request.
- Explain the reasoning in the description. What problem does this solve, and what did you
  consider instead?
- Add tests. For anything touching accounting or parsing, a test is required, not optional.
- If you add a dependency, justify it. Every dependency is a long-term maintenance and
  supply-chain commitment.

## Disagreeing

If you think a design decision in `docs/DECISIONS.md` is wrong, that is a welcome conversation.
Open an issue and argue it. Decisions there are recorded with their reasoning precisely so they
can be challenged rather than inherited.
